# Plan from 2026-11-07: shared import rules, then product detail, news, the other templates

While the readable-settings approach waits for the OK, we prepare everything the stakeholders need to say yes for all templates. Tools in hand: the QA tool (also local, `.qa-tool/local-scripts/qa-server.sh`), CSS blast radius, the authoring rules page, the page cache + fast import, the migration index and decision tables.

## 0. Import scripts per template: one shared rule library, used read-only

### What we measured (2026-11-07)

- **The per-template copies don't diverge; they just stop learnings from spreading.**
  - `tools/importer/product-detail/` and `tools/importer/news-detail-engine/` are about 4,700 lines each; they differ in under 100 lines.
  - Every difference is general AEM component behaviour, none template-specific: phone grids from column controls, `col-md` before `col-sm`, a footnote marker after a bold heading, gradients and cell colours, nested bold, heading em sizes, video posters. Each copy has fixes the other needs.
- **The remaining templates are mostly solved already.**
  - Of the component uses on all 19 remaining templates (from `site.json`), **95.5% are components the library has already run on** (product detail + news).
  - Per template: long page detail 99.3%, tier2 landing 99.7%, base 98.0%, division 100%, package detail 97.6%, procedure detail 92.1%, specialty 78.5%, contact division 71.6%, capability 68.5%, event detail 29%.
  - What's new is a short list, mostly dynamic components: `filteredcontenttypegrid` (specialty, capability, portfolio), `eventdetail`, `productgroups`, `contactus`, `newsandannouncements`, `tagline`, `patenttables`.
- **All 93 AEM components already have a decision** in `decisions/component-map.json` (75 approved, 12 established, 6 skipped).
- **The teammates' importers on main write their fragments with the same path rule as ours** (`xfToFragmentPath` / `xfFragmentPath` → `/us/en/fragments/<AEM path>`: `import-long-page-detail-corp-fragments.js`, `import-news-shared-fragments.js`). Two approaches creating the same XF would overwrite each other's DA document.

### Proposal (revised with the user, 2026-11-07)

**Scope.** The library serves our approach only. The teammates' templates (news-detail, event-detail, contact-division, long-page-detail-corp) are recreated our way, as news-detail-engine was; their importers and fragment documents are not reused.

1. **One rule library**, `tools/importer/corp/`: the engine (section builder, rich text, components, cleanup, DM images, parsers). One handler per AEM component, keyed by the component, with the cases it covers and the source pages that taught them written next to it.
2. **A template profile per template** (in `tools/importer/templates/`, one folder per template), small and owned by the template's owner:
   - its areas in page order (`hero_parsys`, `customizablearea_parsys` …);
   - its page-level pieces (metadata, disclaimer, publish date);
   - its section-style defaults;
   - named overrides with a reason, only where the template really differs.
   - The import script is the engine plus the profile, so a new template is a profile plus handlers for its few new components.
3. **Our own fragments and pages, under our own root.**
   - Every XF our pages use is recreated by our library, once, as a readable-settings fragment document shared by all our templates.
   - The path is the agreed rule (`xfToFragmentPath`, unchanged) under our root: `<root>/us/en/fragments/<AEM path>`. Until approval, all our readable-form pages also go under the root (`<root>/<page path>`), product detail included; the class-form pages at the real paths stay as they are.
   - The teammates' documents are never overwritten, and their pages never pick up ours.
   - On approval, one move strips the root from pages, fragments and the links between them; nothing is re-imported.
4. **Import impact check (the import blast radius)**, which makes the library safe for several people:
   - **Baselines:** per template, a stratified sample (≈ 10 pages, plus their XFs) is imported offline from the page cache (`fast-import.mjs`: same input every time). The output `.plain.html` files are committed as the template's baseline.
   - **On a library change:** `import-impact` re-imports every template's sample and diffs against the baselines (`diff-runs.sh` / `diff-kinds.py`, plus `check-coverage.js`). It reports per template the pages and kinds of change.
   - **Review:** the PR carries the report, and the owners of the changed templates accept their new baselines. That replaces "ask every owner for a regression check" with a scoped, automatic one.
5. **Rule finder (read-only reuse across our templates).** Given an AEM component, a source class or a pattern, it lists our existing handlers, the templates and pages they run on, and the decision-table row. Generated from the handler doc blocks, the component map and the baselines; run before writing a new rule.
6. **Ways of working:**
   - Template work changes only its profile. A general fix goes into the library with the impact report. An override that turns out general is promoted.
   - The library has two reviewers. Every change names the source page that taught it; that's the learnings log.
   - The Block Library's block, variant and section-style names stay the shared vocabulary.

### Steps

**First, the import writes the readable form itself.**
- Today the import scripts still write the class-heavy form; the readable settings come from the converter (`.cbr/local-scripts/settings-convert.mjs`), run afterwards on the imported documents (all 672 product-detail pages were made that way).
- The converter is one function over a document's DOM. It uses the site's `span-tags.js` (which needs only `toClassName` from `aem.js`) and the registry in `corp-settings.js` (no imports). The import scripts are bundled and run in a browser too.
- So the converter's function moves into the library as its last step: the readable-settings writer. It keeps the same code, so the result is the same documents the converter produced, already checked on all 2,023 corp documents (98.6% fully readable; the 27 Statistics `cols-N` classes left).
- Later, where it simplifies a handler, the handler can write the rows directly; the baselines show the output stays the same.

| Step | What | Done when |
|---|---|---|
| 0.1 | Record baselines from today's copies: product detail (10 pages) and news detail engine (10) with their XFs, offline from the page cache; both the class form and the converted form | Committed baselines, reproducible (two imports, no difference) |
| 0.2 | Merge the two copies into `tools/importer/corp/` (the union of their fixes) and switch both templates to engine + profile | Impact report shows only the expected improvements (e.g. product-detail pages gain phone grids), reviewed page by page |
| 0.3 | The readable-settings writer as the library's last step (the converter's function, bundled) | The import output equals the converted baselines; the `style-settings: on` metadata is set by the import |
| 0.4 | Our root `/rs` for fragments and pages: a root option on the path rule, used by our fragment importer and by the page importers' fragment links | A sample page and its XFs import under `/rs`, links included |
| 0.5 | `import-impact` and the rule finder | One command; report per template |
| 0.6 | Recipe for a new template: sample → coverage of its components → profile → import sample → QA at the 4 widths → fix in library or profile → accept baselines → PR | Written into AGENTS.md once the team agrees (it replaces the copy-per-template rule of 2026-11-03) |

## A. Product detail: right at every important width

- **Widths:** 375 (phone), 860 (tablet on both sites), 1100 (desktop on both, below EDS 1200), 1440. They avoid the 600–839 and 900–1023 bands where the two sites differ by design.
- **Run:** all 672 pages, re-imported with the library (readable form, under `/rs`, with our fragments), measured on our branch preview with the local QA tool at 4 widths, 6 threads: about 2 h in the background.
- **Then:**
  - triage worst page first, by cluster;
  - fix by class (library, block CSS, conventions), checking each fix with CSS blast radius and the import impact check;
  - re-run the affected pages;
  - finish with the one-width-only check (`resp-gaps2.py`) and a visual pass at each width on the worst pages.
- **Done when:** every cluster on 2+ pages is fixed or listed as a known source quirk, and the worst 20 pages are reviewed visually at all 4 widths.

## Decisions

- Taken (user, 2026-11-07):
  - the QA in A and B measures our branch preview;
  - the teammates' templates are recreated our way, not reused;
  - XFs are recreated separately for us;
  - a short top-level root for our pages and fragments (`/rs` proposed; one constant);
  - `<name>-engine` where a teammate's template exists (event-detail-engine, contact-division-engine, long-page-detail-engine); other templates keep their plain name;
  - the import writes the readable form itself before anything else (step 0.3).
- Open:
  - the exact root name;
  - the team's agreement on library + profiles + impact check replacing the per-template copies.
